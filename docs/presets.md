# 模式（Agent 预设）

一个**模式**决定三件事：模型是谁（提示词）、手上有什么（工具目录）、被叮嘱了什么（要摘掉哪些骨架提示段）。
它在 dsc 里有三个入口：设置 → 模式（图形编辑）、输入框下方那颗旋钮（切换）、`/preset <名字>`（命令）。

模式就是一个文件：`~/.dsc/presets/<名字>.md`。**形状和 `~/.dsc/agents/<名字>.md`（队友角色）一模一样**，
会写角色就会写模式。

```markdown
---
name: review                    # 模式标识，小写字母数字连字符（缺省取文件名）
label: 代码审查模式               # 界面上的显示名（缺省取 name）
description: 只读地找漏洞与测试缺口，每条结论给「文件名:行号」
tools: read, glob, grep, bash   # 工具白名单（不写 = 全量；写 none = 一个工具都不给）
drop: tool-rules                # 要去掉的骨架提示段（可选，名单见下）
---

你专门找问题，不夸方案。先列出这个方案成立的隐含假设，逐条问「如果不成立会怎样」……
```

正文就是这个模式**追加**进系统提示的那段话（排在「做事方式」之后、「工具规范」之前）。

## 出厂自带的四个

| 标识 | 界面名 | 工具 | 一句话 |
|---|---|---|---|
| `standard` | 标准模式 | 全量 | 处理代码、文件和资料；提示词与出厂完全一致（默认档） |
| `minimal` | 极简模式 | 只有 `bash` | 只给一条 shell（Windows 上是 PowerShell）与固定提示词，用来对照模型的基础表现 |
| `maker` | 创造模式 | 全量 + `runtime_api` | 在标准能力之上加运行时只读查询：给自己加模式、给 dsc 写插件 |
| `ptc` | PTC 模式 | 只有 `run_code` | 模型写一段脚本批量调工具，在代码里筛选汇总，只把结论交回上下文 |

四个文件第一次启动时写出到 `~/.dsc/presets/`，**已存在的一律不覆盖**——你改过的一直是你的。
内置四个删不掉（删了下次启动又会长回来），想改就直接编辑它。

## 可以去掉哪些提示段

`drop` 只认这四个（`core/presets.ts` 的 `DROPPABLE_SECTIONS`）：

| id | 是什么 |
|---|---|
| `behavior` | 做事方式（先看代码再动手、破坏性操作先警告、改完要自查…） |
| `tool-rules` | 工具使用规范（哪个工具干什么、别拿 shell 当万能） |
| `instructions` | 项目说明书（AGENTS.md / CLAUDE.md） |
| `skills` | 技能目录（`<available_skills>`） |

`identity`（中文与称呼约定）与 `environment`（日期、平台、git 分支这些事实）**不在名单里**：
前者是产品约定，后者是事实，都不该被一个模式抹掉。

## 四条硬规矩（改代码时别破）

1. **模式只做减法。** 工具白名单只能是全量的子集（写错名字不报错，生效的是「白名单 ∩ 当前注册表」），
   `drop` 只能去掉上面那四段之一。**任何模式都放宽不了安全**：审批灾难地板、命令策略、路径策略都在代码里，
   看的是命令行与权限模式，不看模式。
2. **默认档必须等价于「没有模式这个概念」。** 标准模式的工具投影是恒等映射、提示段是空串，
   所以系统提示词逐字节不变（服务端提示缓存只认前缀，默认档一变就等于全失效）。
   自检里有这一条断言（`shots/preset-check.mjs`）。
3. **坏文件不许把启动拦下来。** frontmatter 解析不了、`drop` 写了不认识的段、两个文件声明了同一个名字——
   都只是列出来时带一句 `problem`，模型仍按标准档跑。
4. **模式与另外两根旋钮互不越界**：
   - 权限模式（只读 / 自动放行编辑 / 完全访问 / AI 审阅）管「问出来之后怎么裁」；
   - 协作模式（执行 / 计划 / 探索 / 免打扰）管「这一轮允许把手伸多远」；
   - 模式管「模型是谁、手上有什么、被叮嘱了什么」。
   三者各自独立，改一个不会偷偷改另一个。

## 工具与模式的关系

工具条目上可以写 `presets: ['ptc']`（见 `core/tools.ts` 的 `ToolEntry.presets`），意思是
「这个工具只在列出的模式里露面」。`run_code` 标了 `ptc`，`runtime_api` 标了 `maker`，
所以标准模式里看不见它们——标准模式看到的工具目录与出厂时**一模一样**。

反过来，把一个工具名显式写进 `tools:` 白名单，即使它带着别家的模式标签也会露面（你的显式意图优先）。

## PTC 模式的诚实说明

`run_code` 里的脚本跑在**同进程的 `node:vm` 上下文**里：拿不到 `process` / `require` / 文件系统，
唯一的出口是 `sdk`（每个工具一个函数）。但它**没有进程级隔离**——dsh 的 PTC 用的是子进程沙箱，
dsc 这一版不是。换来的是：脚本能做的事 = 它能调用的工具，而工具本身仍受审批与守卫约束，
脚本里每一次 `sdk.xxx()` 都会照旧过一遍守卫链（模式闸门、安全钩子、审批卡）。

脚本里的调用不各自成为一条 `tool` 记录（jsonl 里 tool 记录必须与 assistant 的 `tool_call` 成对，
凭空插一条会让重放出来的请求 400），所以「调了什么、参数是什么、成没成、花了多久」全部写进
`run_code` 的结果正文——模型看到的与日志里存的是同一份。

额度（`core/ptc.ts` 的 `PTC_LIMITS`）：一段脚本最多调 200 次工具、同步段最长 15 秒、
整段最长 120 秒、交回正文最多 20000 字符。
